# Goroutine

## Что такое горутины
<!-- middle 3525480 -->
Горутины - это легковесные потоки выполнения. Они позволяют выполнять функции одновременно (параллельно или конкурентно) без необходимости создавать полноценные потоки операционной системы.

**Легковесность:** Горутины потребляют значительно меньше ресурсов, чем традиционные потоки ОС. Их стек начинается с небольшого размера (обычно несколько килобайт) и может динамически увеличиваться или уменьшаться по мере необходимости.

**Конкурентность:** Горутины работают конкурентно, что означает, что они могут выполняться одновременно, но не обязательно параллельно. Управление их выполнением осуществляется планировщиком Go, который распределяет время выполнения между горутинами.

**Независимость:** Горутины выполняются независимо друг от друга, но могут взаимодействовать через каналы или другие механизмы синхронизации.

**Преимущества:**
1. Упрощение написания конкурентного кода.
2. Эффективное использование ресурсов.

## Lock-free структуры данных
<!-- middle 3525480 -->
Структуры с которыми можно конкурентно работать без блокировок. Это хорошо для производительности и исключает взаимные блокировки.  

Lock-free структуры данных обычно используют атомарные операции, такие как CAS (compare-and-swap), для обеспечения согласованности данных между потоками. Эти операции позволяют потокам соревноваться за изменение данных, но гарантируют, что только один поток сможет успешно изменить данные в любой момент времени.

`sync/atomic` - базовые атомарные операции, на основе которых можно строить lock-free структуры.
`sync.Map` - (частично lock-free) конкурентная map, которая сочетает lock-free подходы с блокировками.  
`chan` - (частично lock-free) используют комбинацию блокировок и lock-free оптимизаций (fast paths, блокировки только при реальной конкуренции).  
`sync/atomic.Value` - полностью lock-free реализация. Гарантирует атомарность операций Store и Load.  
`sync.Once` - (частично lock-free) после инициализации он работает без блокировок.

**Горутина vs Thread**  
Тред имеет фиксированный блок памяти (около 2 МБ) для стека - рабочей области, в котором он хранит локальные переменные.
В горутине такой стек занимает около 2Кб и в отличие от стека потока не является фиксированным. Максимальный размер стека горутины может достигать 1 Гб.

Поток планируется в ядре, каждые несколько миллисекунд аппаратный таймер прерывает процессов, что приводит к вызову функции ядра, именуемой планировщиком.
Планировщик приостанавливает работу текущего потока и сохраняет значения его регистров в памяти (вытесняющая многозадачность?).
Далее планировщик выбирает другой поток, восстанавливает его регистры в памяти и возобновляет его работу (Как он это делает? Из очереди? Есть приоритет?).
Так как переключение потоков планируется в ядре то требуется переключение контекста, а это медленная операция.

Среда выполнения Го имеет собственный планировщик, который использует метод известный как `m:n-планирование` (он мультиплексирует или планирует выполнение m горутин на n потоках ос).
Планировщик Го похож на планировщик ОС, но занимается только горутинами. Планировщик Го вызывается не аапаратным таймером, а при различных условиях (например когда горутина вызывает time.Sleep или блокируются операции канала или мьютекса.).
Планировщик переводит горутину в спящий режим и запускаю другую горутину. Поскольку не переключения контекста планирование горутин происходит намного дешевле потоков.

## Scheduler
<!-- middle 3525480 -->
Планировщик (scheduler) является вытесняющим (preemptive). Начиная с версии 1.14, Go использует асинхронную вытесняющую многозадачность на уровне горутин.
Раньше (до 1.14) планировщик был кооперативным (cooperative), то есть горутина должна была явно уступить управление (например, через runtime.Gosched() или операции ввода-вывода).

**Вытеснение горутины**  
Сейчас планировщик может принудительно вытеснить горутину, если она работает слишком долго (например, в бесконечном цикле без вызовов функций, которые могли бы передать управление).  
Go использует сигналы ОС (например, SIGURG в Unix-системах) для прерывания долго работающих горутин.  
Если горутина выполняется больше 10 мс, планировщик может остановить её и переключиться на другую.

**Кооперация в планировщике**  
Планировщик по-прежнему полагается на кооперацию в некоторых случаях: горутины добровольно уступают управление при вызовах: `time.Sleep()`, `chan`, `Системные вызовы (I/O, мьютексы)`, `runtime.Gosched()`.
Но если горутина не делает таких вызовов, планировщик всё равно вытеснит её через ~10 мс.

## Потокобезопасность
<!-- middle 3525480 -->
От экспортируемых функций уровня пакета обычно ожидается потокобезопасность.
Поскольку переменные уровня пакета не могут быть ограничены одной подпрограммой, функции, которые их изменяют должны обеспечивать взаимное исключение.
Функцию внутри пакета можно разделить на две: с маленькой буквы и с большой (не экспортируемую и экспортируемую), одну из которых сделать с мьютексом, а другую без (что подразумевает, что она будет использована в другой функции, которая захватит блокировку).

**Состояния гонки (race conditions)** в программах на Go возникают, когда несколько горутин (goroutines) одновременно пытаются получить доступ к общим данным, и хотя бы одна из них выполняет запись.

Чтобы избежать гонки можно:
* Не записывать в переменную (инициализировать ее только раз при инициализации пакета), а только читать из нее.
* Управлять переменной только в одном месте в одной функции, а изменения осуществлять по средствам каналов (такая функция называется "монитор" или "подпрограмма управления").


## sync.Mutex
<!-- middle 3525480 -->
Блокировка не реентерабельна (не позволяет блокировать уже заблокированный мьютекс).  

Под капотом мьютекса используются функции из пакета atomic (`atomic.CompareAndSwapInt32` и `atomic.AddInt32`), так что можно считать мьютекс надстройкой над atomic.  
Мьютекс медленнее чем atomic, потому что он блокирует другие горутины на всё время действия блокировки.  

## sync.RWMutex
<!-- middle 3525480 -->
Тратит больше ресурсов, чем обычный Mutex, однако позволяет захватывать себя для чтения сразу нескольким подпрограммам, что выгодно в случае, когда происходит в основном чтение, а не запись.  
По большому счёту, RWMutex это комбинация из двух мьютексов.  

```go
var mu sync.RWMutex
var balance int

func Balance() {
	mu.RLock() // не исключительная блокировка читателя
	defer mu.RUnlock()
	return balanse
}

func Deposit(amount int) {
	mu.Lock() // исключительная блокировка писателя
	defer mu.Unlock()
	deposit += amount
}
```

## sync.Cond
<!-- middle 3525480 -->
Это механизм синхронизации, который позволяет горутинам ожидать или объявлять о наступлении некоторого события.  
```go
var (
    mu    sync.Mutex
    cond  = sync.NewCond(&mu)
    ready bool
)

// Ожидающая горутина
go func() {
    mu.Lock()
    for !ready {
        cond.Wait() // Ждем, пока ready не станет true
    }
    // Выполняем работу
    mu.Unlock()
}()

// Сигнализирующая горутина
go func() {
    mu.Lock()
    ready = true
    cond.Signal() // или Broadcast()
    mu.Unlock()
}()
```

## sync/atomic
<!-- middle 3525480 -->
Атомарная операция выполняется за один шаг относительно других потоков или, в контексте Go, других горутин. Это означает, что атомарную операцию нельзя прервать в середине ее работы.  

Стандартная библиотека Go содержит пакет atomic, который в некоторых простых случаях может помочь избежать использования мьютекса. С помощью него мы получаем доступ к атомарным счетчикам из нескольких горутин, не имея проблем с синхронизацией и не беспокоясь о race condition.
