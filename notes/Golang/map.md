# Map

## Как работает map
<!-- junior 3525480 -->
Ключами в map могут быть типы данных, которые поддерживают операцию сравнения на равенство (==).
Это означает, что ключом может быть любой тип, который можно сравнивать с другим значением того же типа.
Хэш таблицы дают только поверхностные копии своих ключей.  Равенство для ключа должно быть неизменным на протяжении всей жизни хэш таблицы.  
Ключом может быть любое сравниваемое значение, но использовать числа с плавающей точкой плохая идея.
```go
m := map[string]int{"x": 0}
v, ok := m["y"] // 0 false
```

## Ключи
<!-- junior 3525480 -->
Могут быть ключами в map:  
Числа, строки, bool, uintptr, pointer (на типы, которые сами по себе могут быть ключами), channel  
interface (если динамическое значение, хранящееся в интерфейсе, поддерживает сравнение)  
array (если элементы массива поддерживают сравнение)  
struct (если все поля структуры поддерживают сравнение)

Не могут быть ключами в map:  
slice, func, map

Значениями map могут быть любые типы данных, однако, если используется интерфейс (тип данных заранее не определен) то придется приводить к явному типу.

## Порядок ключей
<!-- junior 3525480 -->
Из-за эвакуации, безопасности, изменений реализации, оптимизации производительности порядок ключей не гарантирован.

В Go 1.12 порядок стал еще более случайным между запусками программы (добавлен seed при инициализации map). Это изменение было сделано специально, чтобы ловить код, который неявно полагается на порядок.
`fmt.Println` сортирует ключи перед выводом.

Если нужно сохранить порядок, то можно использовать слайс или массив для ключей и итерироваться по нему.

## Эвакуация данных
<!-- middle 3525480 -->
При использовании типа map может происходить так называемая "эвакуация данных" (data evacuation) или перераспределение элементов при изменении размера хеш-таблицы.

Происходит в следующих случаях:
* Когда количество элементов в map превышает определенный порог (примерно 6.5 элементов на бакет), Go увеличивает количество бакетов и перераспределяет элементы.
* При частых вставках и удалениях - если map испытывает много операций удаления, это может привести к фрагментации бакетов и необходимости реорганизации.

**Как избежать эвакуации данных**  
1 Инициализация с нужным размером. Это выделит достаточно бакетов сразу, избегая перераспределения.
```go
// Указываем предполагаемый размер при создании
m := make(map[string]int, 1000)
```
2 Избегать частых вставок/удалений. Если возможно, заполняйте map один раз и затем только читайте. Использовать других структур данных для сценариев с частыми изменениями.

Эвакуация происходит не сразу, поэтому приходится искать элементы и в старых и в новых бакетах.  

Из-за эвакуации нельзя получить указатель на значение.

## Новая реализация Map

В Go 1.24 встроенная реализация map была полностью переработана и теперь основана на Swiss Table.  
Улучшили механизм разрешения коллизий, теперь для небольших map выделяется меньше памяти.  
Это особенно полезно для нагруженных сервисов с большим количеством маленьких map.

## sync.Map
<!-- middle 3525480 -->
Это конкурентно-безопасная реализация map, которая использует следующие техники для эффективной работы в многопоточной среде:
1. **Двойная структура данных**: использует два отдельных map (dirty и read) для минимизации блокировок
2. **Оптимизация для чтения**: операции чтения обычно работают с атомарным доступом к read-only map без блокировок
3. **Отложенные записи**: изменения сначала накапливаются в dirty map, а затем продвигаются в read map
4. **Атомарные указатели**: для переключения между read и dirty map используются атомарные операции

Используйте `sync.Map` в следующих случаях:
1. **Высокая конкуренция при чтении**, но редкие записи (read-heavy workload)
2. **Кэширование** в многопоточной среде
3. **Сценарии, где ключи часто читаются**, но редко перезаписываются
4. **Когда разные горутины используют разные наборы ключей**

Избегайте `sync.Map` в таких ситуациях:
1. **Частые записи** (write-heavy workload) - обычный `map` с `sync.Mutex`/`sync.RWMutex` будет эффективнее
2. **Когда нужны атомарные сложные операции** над map (например, проверка-и-добавление)
3. **Требуется предсказуемая производительность** - `sync.Map` может иметь провалы при продвижении dirty map
4. **Небольшие map** - накладные расходы на синхронизацию могут перевесить преимущества

```go
var m sync.Map

// Хранение значения
m.Store("key", "value")

// Получение значения
if value, ok := m.Load("key"); ok {
    fmt.Println(value)
}

// Удаление
m.Delete("key")

// Атомарное обновление
m.LoadOrStore("newKey", 42)
```

Для других сценариев рассмотрите:
- Обычный `map` с `sync.Mutex` для write-heavy workload
- `sync.RWMutex` для read-heavy workload с редкими записями
- Шардированные map для уменьшения конкуренции

`sync.Map` оптимизирован для специфических случаев и не является заменой обычным синхронизированным map во всех ситуациях.

## Изменение map при итерации по ней
<!-- junior 3525480 -->
Не стоит одновременно итерироваться и изменять `map`.
Если во время итерации создается элемент мапы, он может быть обработан во время итерации или пропущен. Выбор может варьироваться для каждого созданного элемента и от одной итерации к другой.
Это происходит из-за того, что при добавлении новых элементов map может рехешироваться (изменять свою внутреннюю структуру).  
Это поведение намеренно оставлено неопределённым для: Предоставления свободы реализации, Предотвращения зависимости от конкретного поведения, Возможности оптимизации в будущем.

Удаление элементов может вызвать concurrent map iteration and map write.
