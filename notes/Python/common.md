# Общие вопросы

## Как устроен python
<!-- junior 3525480 -->
**Python** - интерпретируемый язык программирования. Он не конвертирует свой код в машинный, который понимает железо (в отличие от С и С++). Вместо этого, Python-интерпретатор переводит код программы в байт-код, который запускается на виртуальной машине Python (PVM).

**CPython** - интерпретатор компилирующего типа (благодаря этому достигается большее быстродействие выполнения программ). Считается эталонной реализацией языка Python.

**Интерпретатор компилирующего типа** - это система из компилятора и интерпретатора. Компилятор переводит исходный код программы в промежуточное представление (байт-код), а интерпретатор (виртуальная машина) выполняет этот байт-код.

**Байт-код** - низкоуровневое, платформа-независимое представление исходного кода для виртуальной машины.

**.pyc** - файлы в которых хранится байт-код. Если исходный текст программы не изменился с момента последней компиляции, при следующем запуске вашей программы, Python сразу загрузит файл .pyc, минуя этап компиляции (тем самым ускорит процесс запуска программы). Эти файлы создаются только при импортировании модуля в другой модуль.

**Python Virtual Machine** - является частью Python-интерпретатора. По сути это просто большой цикл, который выполняет перебор инструкций в байт-коде и выполняет соответствующие им операции. Цикл выполнения байт-кода - это бесконечный цикл, который содержит гигантский switch всех возможных инструкций байт-кода.

## Спецификаторы доступа
<!-- junior 3525480 -->
**Protected** - начинается с "_" одинарного нижнего подчеркивания. Доступен только в классе и его потомках.

**Private** - начинается с "\__" двойного нижнего подчеркивания. Доступен только в самом классе. По имени вызвать нельзя, но можно через специальную конструкцию: _{ИмяКласа}__{ИмяСвойства}.

## Область видимости
<!-- junior 3525480 -->
Python ищет переменные в следующем порядке (LEGB):
* L (Local) - локальная область видимости.
* E (Enclosing) - область видимости вложенных функций (nonlocal область).
* G (Global) - глобальная область видимости.
* B (Built-in) - встроенная область видимости.

**Глобальные переменные**  
Чтобы изменять глобальную переменную (объявленную вне функции) нужно использовать ключевое слово global. Читать глобальные переменные никто не мешает. Вне функции это ключевое слово не имеет смысла.

**Nonlocal переменные**  
Ключевое слово nonlocal используется для указания того, что переменная, которую вы хотите изменить внутри вложенной функции, относится к ближайшей enclosing (охватывающей) области видимости, но не к глобальной. Это позволяет изменять значение переменной, которая находится в области видимости внешней функции, но не является глобальной.

```python
def func():
    x = 'local'
    y = 'local'

    def nested_func():
        global x
        nonlocal y
        x = 'global'
        y = 'nonlocal'

    print(x, y)  # local, local
    nested_func()
    print(x, y)  # local, nonlocal


func()
print(x)  # global
print(y)  # error y not defined
```

## Декораторы
<!-- junior 3525480 -->
Декоратор - это функция, которая позволяет обернуть другую функцию для изменения ее функционала без изменения ее кода.
Чтобы создать декоратор с параметрами нужно обернуть декоратор в еще одну функцию так как декоратор принимает только один параметр - декорируемую функцию.
```python
from functools import wraps

""" decorator without parameters """
def decor1(func):
    @wraps(func)
    def wrapper(*args, **kwargs):
        """ new code """
        return func(*args, **kwargs)
    return wrapper

""" decorator with parameters """
def decor2(param1, param2):
    def _decor2(func):
        @wraps(func)
        def wrapper(*args, **kwargs):
            """ new code, param1 and param2 available here """
            return func(*args, **kwargs)
        return wrapper
    return _decor2

""" class-based decorator """
class CacheDecor:
    def __init__(self, driver):
        self.driver = driver
    
    def __call__(self, ttl_sec):
        """ param decorator """
        pass
```

## Метаклассы
<!-- junior 3525480 -->
Метакласы нужны для програмного создания классов. В питоне класс это нечто большее - классы также являются объектами. Основное применение это создание красивых API для конечного пользователя (например Django ORM).
```python
class MyMetaclass(type): 
    def __new__(cls, name, bases, dct):

```

## Method Resolution Order
<!-- middle 3525480 -->
Порядок разрешения методов - относится не только к методам, но и к прочим атрибутам класса, так как методы - это частный случай более общего понятия «атрибут».

Из-за введения базового класса object от которого неявно наследуются все объекты появилась diamond problem и чтобы ее решить применяют алгоритм С3.

С помощью метакласса можно изменить MRO переопределением type.mro(cls):
```python
class MyMRO(type):  # наследование type = это метакласс
    def mro(cls):
        return (cls, A, B, X, Y, object)  # явно задаем порядок!
```

Алгорит C3 работает не всегда, например:
```python
O = object
class X(O): pass
class Y(O): pass
class A(X, Y): pass
class B(Y, X): pass
class C(A, B): ...
""" TypeError: Cannot create a consistent method resolution order (MRO) for bases X, Y """
```

## Хеш таблица
<!-- middle 3525480 -->
Хеш-таблица - это структура данных, с помощью которой реализуется механизм ассоциативного массива. Поиск, вставка, удаление обычно занимает О(1).  
В основе ХТ лежит массив. На основе ключа высчитывается индекс массива (целочисленный хэш % размер массива).  

Иногда для двух разных значений получается одинаковый хэш - такая ситуация называется коллизией. Возникает такая ситуация потому, что хэш-функция принимает значение переменной длинны, а возвращает хэш постоянной длинны.

Когда количество элементов в таблице превышает определенный порог (обычно 2/3 от текущего размера), таблица расширяется, чтобы уменьшить вероятность коллизий. При расширении все ключи перехэшируются и размещаются в новой таблице большего размера.

Открытая адресация - метод разрешения коллизий используемый в Python. В этом случае в ячейки помещаются пары ключ-значение. Алгоритм такой: вычисляем хеш-функцию, проверяем нужную ячейку (что она не пустая и значение совпадает). Если искомого элемента нет, то ищем в следующей ячейке. Аналогично при вставке - если ячейка не пустая то применяем "алгоритм" изменяем индекс и пробуем следующую ячейку и так пока не найдем свободную. 

Метод цепочек - связанный список на все элементы с нужным индексом. Не используется в питоне из-за расходов на дополнительные структуры данных.

## Память
<!-- middle 3525480 -->
Память выделять затратно поэтому существует ряд оптимизаций. Аллокатор в питоне состоит из трех частей:  
* Арена - большой непрерывный кусок памяти (обычно 256 килобайт), содержит несколько страниц виртуальной памяти операционной системы.
* Пул - одна страница виртуальной памяти (обычно 4 килобайта) Все блоки одинакового размера.
* Блок - маленький кусочек памяти, используемый для хранения одного объекта.

Память не выделяется на прямую, менеджер памяти ищет подходящее место в блоке. Если же свободных блоков нет или же пулов нужного размера нет, верхний менеджер выдает новый пул из наиболее заполненной арены. Если и все арены заняты, запрашивается новая арена.
```python
import sys

class A:
    pass

""" Размер в байтах: """
print(sys.getsizeof(list()))  # 56
print(sys.getsizeof(tuple()))  # 40 за счет неизменяемости хранит меньше информации
print(sys.getsizeof(dict()))  # 64
print(sys.getsizeof(set()))  # 216 множество заранее резервирует больше места
print(sys.getsizeof(1))  # 28
print(sys.getsizeof(''))  # 41
print(sys.getsizeof(True))  # 28
print(sys.getsizeof(None))  # 16
print(sys.getsizeof(A()))  # 48
```

## Стек и Куча
<!-- middle 3525480 -->
Python использует собственный менеджер памяти (PyMalloc) и не дает прямого доступа к стеку/куче как в C.

Стек - это область оперативной памяти, которая создаётся для каждого потока. Он работает в порядке LIFO.  
Используется для:
- Хранения фреймов вызовов функций
- Локальных переменных функций
- Возвращаемых адресов

Куча - это основное хранилище для объектов Python. Здесь хранится:
- Все создаваемые объекты (списки, словари, строки, экземпляры классов)
- Данные, которые должны жить дольше вызова функции

## Сборка мусора
<!-- middle 3525480 -->
Стандартный интерпретатор питона (CPython) использует сразу два алгоритма, подсчет ссылок и generational garbage collector (GC), более известный как стандартный модуль gc из Python.

Алгоритм подсчета ссылок очень простой и эффективный, но у него есть один большой недостаток. Он не умеет определять циклические ссылки. Именно из-за этого, в питоне существует дополнительный сборщик, именуемый поколенческий GC, который следит за объектами с потенциальными циклическими ссылками.

Алгоритм подсчета ссылок это одна из самых простых техник для сборки мусора. Объекты удаляются как только на них больше нет ссылок. Каждый объект в Python содержит дополнительное поле (счетчик ссылок), в котором хранится количество ссылок на него. Как только кто-то ссылается на объект, это поле увеличивается на единицу. Если по какой-то причине ссылка пропадает, то это поле уменьшается на один.

Переменные, которые объявлены вне функций, классов и блоков называются глобальными. Как правило, жизненный цикл таких переменных равен жизни Python процесса. Таким образом, количество ссылок на объекты на которые ссылаются глобальные переменные никогда не падает до нуля. У данного алгоритма есть множество проблем, таких как циклические ссылки, блокирование потоков, а также дополнительные накладные расходы на память и cpu. Основным плюсом этого алгоритма является то, что объекты удаляются сразу как только они не нужны.

Классический алгоритм подсчета ссылок имеет один большой недостаток - он не умеет находить циклические ссылки. Циклические ссылки происходят когда один или более объектов ссылаются на друг друга. Циклические ссылки могут происходить только в “контейнерных” объектах. Т.е. в объектах, которые могут хранить другие объекты, например в списках, словарях, классах и кортежах.

В отличие от алгоритма подсчета ссылок, циклический GC не работает в режиме реального времени и запускается периодически. Каждый запуск сборщика создаёт микропаузы в работе кода, поэтому CPython использует различные эвристики, для определения частоты запуска сборщика мусора.

GC разделяет все объекты на 3 поколения (генерации). Новые объекты попадают в первое поколение. Если новый объект выживает процесс сборки мусора, то он перемещается в следующее поколение. Чем выше поколение, тем реже оно сканируется на мусор. Так-как новые объекты зачастую имеют очень маленький срок жизни (являются временными), то имеет смысл опрашивать их чаще, чем те, которые уже прошли через несколько этапов сборки мусора.

## Copy on write
<!-- middle 3525480 -->
Копирование при записи - идея подхода copy-on-write заключается в том, что при чтении области данных используется общая копия, в случае изменения данных - создается новая копия.

В ядре Linux существует механизм копирования при записи (Copy-on-Write, CoW), который служит для оптимизации работы дочерних процессов. Дочерний процесс в начале своего существования делит каждую страницу памяти со своим родителем. Страница копируется в собственную память процесса только при записи.

Но в мире Python из-за подсчета ссылок происходят интересные вещи. Каждый раз при чтении Python-объекта интерпретатор увеличит его счетчик ссылок, что в сущности является операцией записи в его внутреннюю структуру данных. Это вызывает CoW. Получается, что с Python мы на самом деле используем Copy-on-Read (CoR)!  
Если этот объект находится в разделяемой памяти (например, при использовании multiprocessing с CoW-механизмами ОС), то такая "запись при чтении" заставляет систему создать физическую копию данных.

## Generic
<!-- junior 3525480 -->
Дженерики полезны когда нужно сохранить информацию о типе, при этом не фиксируя его жестко. Например, контейнер, который хранит однотипные данные. Или функция, которая возвращает данные того же типа, что и один из аргументов. Примеры встроеных дженериков: типы List, Callable.

Чтобы создать собственный дженерик-тип  нужно создать TypeVar переменную, которая будет атрибутом дженерика и объявить generic-тип:
```python
from typing import TypeVar, Generic

T = TypeVar('T')

class LinkedList(Generic[T]):
    data: T
```
T = TypeVar('T')  # Может быть любым типом  
S = TypeVar('S', bound=str)  # Может быть любым подтипом str  
A = TypeVar('A', str, bytes)  # Должен быть str либо bytes

## __ new __ vs __ init __
<!-- junior 3525480 -->
\_\_new__ - это конструктор класса, вызывается для создания нового экземпляра класса.
\_\_init__ - инициализирует возвращенный методом \_\_new__ объект.

Ключевые случаи использования \_\_new__:
- Работа с неизменяемыми (immutable) типами
- Создание синглтонов (Singleton)
- Возврат объектов другого типа
- Кэширование объектов (object pooling)

```python
class Person:
    def __new__(cls, name, age):  # вызывается перед __init__
        print(f"Creating person: {name}")
        return super().__new__(cls)
    
    def __init__(self, name, age):
        self.name = name
        self.age = age

p = Person("Alice", 30)  # Одинаковые аргументы в оба метода
```

## Что может быть ключом словаря

Ключами могут быть не изменяемые типы данных.  
Float как ключ - возможно, но опасно (из-за погрешности float).
Кортежи если они не содержат изменяемые типы.  
Если у объекта реализованы оба метода \_\_hash__ и \_\_eq__.  

## Slots
<!-- junior 3525480 -->
\_\_slots__ - позволяет точно описать какие атрибуты будут у объекта. Благодаря этому не будет создаваться словарь атрибутов.

❌Потеря гибкости
❌При наследовании нужно снова прописывать слоты
❌Нельзя использовать @property без явного слота
❌Проблемы с сериализацией (pickle)
❌Выигрыш в памяти часто незначителен
❌Производительность не всегда лучше
❌Сложность отладки
❌Многие библиотеки и фреймворки полагаются на динамическое добавление атрибутов

✅Создаётся очень много экземпляров (миллионы)
✅Immutable-объекты
✅Библиотеки для высоконагруженных систем

В свежих версиях питона слоты не очень актуальны из-за PEP 412 (Разделяемые ключи в словарях)
