# Architecture

## Минусы архитектур
Минусы архитектур - они могут препятствовать здравому смыслу в конкретном примере и требовать больше времени на построение и поддержку в нужном виде.

## Clean architecture
Это подход к проектированию программного обеспечения, предложенный Робертом Мартином (Uncle Bob).

Цель сделать систему:
1. Независимой от фреймворков
2. Тестируемой
3. Легко изменяемой
4. Понятной

Основные принципы:
1. Разделение на слои с четкими правилами зависимостей.
2. Бизнес-логика изолирована от деталей реализации (UI, БД, внешние сервисы).
3. Зависимости направлены внутрь (от внешних слоев к ядру).

Слои чистой архитектуры:
1. Entities (Сущности) - Бизнес-объекты (например, User, Order).
2. Use Cases (Сценарии использования) - Бизнес-правила и логика (например, "Создать заказ").
3. Interface Adapters (Адаптеры) - Преобразует данные между Use Cases и внешним миром.
4. Frameworks & Drivers (Внешние инструменты) - Внешние технологии (БД, веб-фреймворки, UI).

Правило зависимостей:
1. Внутренние слои не зависят от внешних.
2. Зависимости направлены к центру: Фреймворки → Адаптеры → Use Cases → Entities
 
Плюсы:  
✅ Независимость от технологий: можно заменить БД или фреймворк без изменения бизнес-логики.  
✅ Тестируемость: use Cases тестируются без HTTP/БД (моки).  
✅ Гибкость: легко добавлять новые адаптеры (например, CLI поверх API).  
✅ Долгосрочная поддержка: Код остается чистым даже при росте проекта.  

Минусы:  
❌ Много маппингов структур между слоями  
❌ Нужен DI-контейнер, иначе при развитии проекта становится сложно уже не в бизнес логике, а в инициализации зависимостей  
❌ Поход репозиториев требует какого-то решения для транзакций. Зачастую это усложняет код, приводит к утечке абстракции в слой бизнес-логики и при определенных реализациях также может замедлить выполнение  
❌ Зачастую в юзкейсах есть общий код, который надо куда-то выделить. При этом не хочется каждый раз в функции пробрасывать зависимости  
❌ Как реализовать паттерн outbox в репозитории без утечки абстракции и кросс зависимости между адаптерами?  

Dependency Injection (DI) - ключевой механизм для соблюдения принципов чистой архитектуры.  


## Onion architecture (OA)
Onion Architecture можно считать частным случаем Clean Architecture с более явным выделением Domain Layer.  

Основные слои:
1. Domain Layer – ядро (Entities + бизнес-логика).
2. Application Layer – Use Cases, сервисы.
3. Infrastructure Layer – реализация репозиториев, внешние API.
4. UI/Presentation Layer – контроллеры, API-роуты.

Для микросервисов → Clean Architecture (лучше сочетается с CQRS/Event Sourcing).  
Для монолитов с бизнес-логикой → Onion Architecture.  


## Hexagonal Architecture (HA)
Это архитектурный подход, который ставит бизнес-логику в центр, а все внешние взаимодействия (БД, API, UI) делает "подключаемыми" через адаптеры. Название "гексагональная" условное — речь не о шестиугольниках, а о разделении на ядро и внешние компоненты.

Ключевые принципы:
1. Ядро (Core) - Содержит бизнес-логику (Domain Model, Use Cases). Не зависит от внешнего мира (нет упоминаний о БД, HTTP и т.д.).
2. Порты (Ports) - Интерфейсы для взаимодействия с внешним миром. Определяются ядром (например, PaymentGateway, UserRepository).
3. Адаптеры (Adapters) - Реализуют порты для конкретных технологий. Бывают: Входные (Driving Adapters): API, CLI, Kafka потребители. Выходные (Driven Adapters): Реализации репозиториев (PostgreSQL, Redis).

## Event-Driven Architecture (EDA)
Это архитектурный паттерн, в котором система реагирует на события (изменения состояния, действия пользователей, сообщения от других систем) асинхронно, вместо традиционного последовательного выполнения кода.

1. Производитель генерирует событие (например, "заказ создан").
2. Брокер получает событие и направляет его всем подписанным потребителям.
3. Потребители обрабатывают событие (например, "отправить email", "обновить склад", "запустить аналитику").

Плюсы:  
✅ Гибкость и масштабируемость – компоненты слабо связаны, можно добавлять новых потребителей без изменения продюсеров.  
✅ Асинхронность – система не блокируется, пока ждет ответа.  
✅ Отказоустойчивость – если один сервис упал, события могут быть обработаны позже (благодаря очереди сообщений).  
✅ Реактивность – система мгновенно реагирует на изменения.  

Минусы:  
❌ Сложность отладки – из-за асинхронности трудно отслеживать цепочки событий.  
❌ Гарантия доставки – нужно продумывать механизмы повторной отправки и идемпотентности.  
❌ Event Storming – проектирование событийной модели требует дополнительных усилий.  


## Plugin architecture (PA)
Это подход к проектированию программного обеспечения, при котором основное приложение (ядро) поддерживает динамическое подключение дополнительных модулей (плагинов) для расширения функциональности без изменения исходного кода.

Основные принципы:
1. Ядро (Core) – базовая система, предоставляющая:
    * API для взаимодействия с плагинами
    * Жизненный цикл (загрузка, инициализация, выгрузка)
    * Механизм обнаружения плагинов (например, сканирование папки /plugins)
2. Плагины (Plugins) – независимые модули, которые:
    * Реализуют определенный интерфейс/контракт
    * Расширяют функциональность ядра (например, новые фильтры в Photoshop, дополнения в IDE)
3. Связь между ядром и плагинами:
    * Через интерфейсы (абстракции),
    * Через события (если используется Event-Driven подход),
    * Через DI (Dependency Injection).

Плюсы:  
✅ Гибкость и расширяемость  
✅ Упрощение тестирования (плагинов по отдельности)  
✅ Плагины может писать человек не знакомый со всей системой  
✅ Плагины могут быть написаны на разных языках  

Минусы:  
❌ Сложность проектирования (Нужно тщательно продумывать интерфейсы)  
❌ Усложнение отладки ядра (особенно если плагины загружаются динамически)  
❌ Производительность (плагины могут добавлять накладные расходы)  
❌ Плагины могут требовать разные версии библиотек  


## Event sourcing architecture (ESA)
Это архитектурный подход, при котором состояние системы определяется последовательностью событий, а не просто последним "снимком" данных. Вместо обновления записи в БД система сохраняет каждое изменение как неизменяемое событие, которое можно воспроизвести для восстановления состояния.

Основные принципы:  
1. Событие (Event) – факт изменения состояния (например, UserRegistered, OrderPaid, BalanceUpdated).
2. Event Store – база, где хранятся все события в хронологическом порядке.
3. Aggregate (Агрегат) – объект, состояние которого строится из событий.
4. Projection (Проекция) – представление данных, полученное из событий (например, SQL-таблица или документ в MongoDB).
5. Command (Команда) – действие, которое может породить событие (например, RegisterUserCommand).

Плюсы:  
✅ Полная история изменений (можно восстановить состояние на любой момент времени)  
✅ Отказоустойчивость  
✅ Гибкость в аналитике  
✅ Поддержка сложных бизнес-процессов  
✅ Интеграция с Event-Driven Architecture  

Минусы:  
❌ Сложность реализации (нужно продумывать структуру событий, агрегатов и проекций)  
❌ Производительность (восстановление состояния агрегата из тысяч событий может быть медленным)  
❌ Сложность запросов для аналитики  
❌ Риск дублирования событий  
❌ Миграции данных сложнее (например изменение структуры события)  


## Domain-Driven Design (DDD)
Это подход к разработке сложного программного обеспечения, который фокусируется на глубоком понимании бизнес-логики и её точном отражении в коде. Основная идея — строить архитектуру вокруг домена (предметной области), а не вокруг технологий (баз данных, фреймворков).

Строительные блоки DDD:
1. Сущность (Entity) – объект с уникальным идентификатором (например, User с userId).
2. Значение (Value Object) – объект без идентификатора (например, Address).
3. Агрегат (Aggregate) – кластер связанных объектов, управляемый корневой сущностью (например, Order + OrderItems).
4. Репозиторий (Repository) – интерфейс для доступа к агрегатам (как коллекциям в памяти).
5. Сервис домена (Domain Service) – логика, которая не принадлежит сущностям/значениям.
6. Событие домена (Domain Event) – факт, значимый для бизнеса (например, OrderShipped).

Слои архитектуры в DDD:  
1. Доменнный слой – ядро с бизнес-логикой (сущности, агрегаты).
2. Прикладной слой (Application Layer) – координирует задачи (например, обработка PlaceOrderCommand).
3. Инфраструктурный слой – технические детали (БД, API, кеш).

Плюсы:  
✅ Чистая бизнес-логика – код отражает реальные процессы, а не структуру БД.  
✅ Масштабируемость – ограниченные контексты уменьшают сложность.  
✅ Гибкость – легче адаптироваться к изменениям требований.  
✅ Командная работа – универсальный язык улучшает коммуникацию.  

Минусы:  
❌ Сложность – избыточен для простых CRUD-приложений.  
❌ Время на проектирование – требует глубокого погружения в домен.  
❌ Оверкилл – если бизнес-правила простые, DDD может замедлить разработку.

## Service-Oriented Architecture (SOA)
Это архитектурный стиль, в котором приложение строится как набор взаимодействующих сервисов, каждый из которых выполняет свою бизнес-функцию и доступен через стандартизированные интерфейсы (чаще всего через сеть).

## SOA vs Микросервисы
| **Критерий**       | **SOA**                  | **Микросервисы**         |
|--------------------|--------------------------|--------------------------|
| **Размер сервиса** | Крупный (бизнес-функция) | Мелкий (одна задача)     |
| **Коммуникация**   | Часто через ESB          | Прямые вызовы (REST/RPC) |
| **Данные**         | Возможны общие БД        | Каждый сервис — своя БД  |
| **Гибкость**       | Менее гибкая             | Более agile              |

> **SOA** — предшественник микросервисов, больше подходит для корпоративных систем.  
> **Микросервисы** — эволюция SOA с упором на автономность и DevOps.


## Command Query Responsibility Segregation (CQRS)
Это архитектурный шаблон, который разделяет операции чтения (Query) и записи (Command) данных на разные модели.

Ключевые идеи:
1. Команды (Commands) — изменяют состояние (например, CreateOrder, UpdateUser), работают через модель записи.
2. Запросы (Queries) — только читают данные (например, GetOrderDetails, ListProducts), используют модель чтения.
3. Разные модели — могут иметь отдельные БД, схемы или даже технологии (например, SQL для команд, Redis для запросов).

Плюсы:  
✅ Производительность — оптимизированные модели под свои задачи (например, денормализованная БД для чтения).  
✅ Масштабируемость — чтение и запись можно масштабировать независимо.  
✅ Гибкость — разные модели для сложных сценариев (аналитика, отчеты).  

Минусы:  
❌ Сложность — две модели = больше кода и инфраструктуры.  
❌ Согласованность — задержка между обновлением записи и актуальностью данных для чтения (eventual consistency).  

Где использовать:
1. Системы с высокой нагрузкой на чтение (например, соцсети, маркетплейсы).
2. Сложные отчеты и аналитика.
3. В сочетании с Event Sourcing (история изменений как события).
