# PostgreSQL

## Первичный ключ
Первичный ключ или PRIMARY KEY предназначен для однозначной идентификации каждой записи в таблице и является строго уникальным (UNIQUE): две записи таблицы не могут иметь одинаковые значения первичного ключа. Нулевые значения (NULL) в PRIMARY KEY не допускаются. Если в качестве PRIMARY KEY используется несколько полей, их называют составным ключом. Обычно это поле ID.

## Внешний ключ
Внешний ключ или FOREIGN KEY также является атрибутом ограничения и обеспечивает связь двух таблиц. По сути, это поле или несколько полей, которые ссылаются на PRIMARY KEY или UNIQUE в родительской таблице. Первичный ключ может быть null.

Также с помощью него можно задать поведение при редактировании и удалении родительской записи (ON DELETE, ON UPDATE): RESTRICT, CASCADE, SET NULL,  
NO ACTION, SET DEFAULT.

## SQL-ограничения (constraints)
Указываются при создании или изменении таблицы. Это правила для ограничения типа данных, которые могут храниться в таблице. Действие с данными не будет выполнено, если нарушаются установленные ограничения.

UNIQUE - гарантирует уникальность значений в столбце.  
NOT NULL - значение не может быть NULL.  
CHECK - значения столбца должны соответствовать заданным условиям.  
DEFAULT - предоставляет столбцу значения по умолчанию.  

## Типы join
Чтобы объединить две таблицы в одну, следует использовать оператор JOIN. Соединение таблиц может быть внутренним (INNER) или внешним (OUTER), причём внешнее соединение может быть левым (LEFT), правым (RIGHT) или полным (FULL).

INNER JOIN - получение записей с одинаковыми значениями в обеих таблицах, т.е. получение пересечения таблиц.

FULL OUTER JOIN - объединяет записи из обеих таблиц (если условие объединения равно true) и дополняет их всеми записями из обеих таблиц, которые не имеют совпадений. Для записей, которые не имеют совпадений из другой таблицы, недостающее поле будет иметь значение NULL.

LEFT OUTER JOIN - возвращает все записи, удовлетворяющие условию объединения, плюс все оставшиеся записи из внешней (левой) таблицы, которые не удовлетворяют условию объединения.

RIGHT OUTER JOIN - работает точно так же, как и левое объединение, только в качестве внешней таблицы будет использоваться правая.

CROSS OUTER JOIN - Эта операция просто объединяет каждую строку первой таблицы с каждой строкой второй таблицы (декартово произведение). В результате получается таблица со всеми возможными сочетаниями строк обеих таблиц. В операторе за ненадобностью отсутствует условие ON.

## Оператор UNION
Он используется для объединения полученных данных из двух или более запросов, которые должны иметь одинаковое количество столбцов с одинаковыми типами данных и расположенных в том же порядке. Полностью одинаковые строки будут объеденены. Чтобы включить дубли в результат нужно использовать UNION ALL.

## Оператор INSERT INTO SELECT
Данный оператор копирует данные из одной таблицы и вставляет их в другую, при этом типы данных в обеих таблицах должны соответствовать.

## Оператор HAVING
Оператор HAVING работает почти так же, как и WHERE, вот только применяется не для всех столбцов, а для набора, созданного оператором GROUP BY.

## Оператор DISTINCT
Используется для указания на то, что следует работать только с уникальными значениями столбца. SELECT DISTINCT column_name FROM table_name. Столбцов может быть несколько.

## Оконные функции
Функция, которая работает с выделенным набором строк (окном, партицией) и выполняет вычисление для этого набора строк в отдельном столбце.

Партиции (окна из набора строк) - это набор строк, указанный для оконной функции по одному из столбцов или группе столбцов таблицы.

В отличии от GROUP BY оконная функция не сокращает колличество строк в результате.

**Агрегирующие** - можно применять любую из агрегирующих функций - SUM, AVG, COUNT, MIN, MAX.  
**Ранжирующие** - в ранжирующих функция под ключевым словом OVER обязательным идет указание условия ORDER BY, по которому будет происходить сортировка ранжирования. ROW_NUMBER  
**Функции смещения** - функции, которые позволяют перемещаясь по выделенной партиции таблицы обращаться к предыдущему значению строки или крайним значениям строк в партиции. LAG (предыдущее значение столбца), LEAD (следующее значение столбца).

## Транзакции
Транзакция - это группировка нескольких операций. Транзакция может понадобиться для выполнения операций атомарно, для конкурентного доступа к записям, для отката изменений в случае ошибки.

Операторами в транзакции можно также управлять на более детальном уровне, используя точки сохранения. Точки сохранения позволяют выборочно отменять некоторые части транзакции и фиксировать все остальные. Определив точку сохранения с помощью SAVEPOINT (вложенные транзакции), при необходимости вы можете вернуться к ней с помощью команды ROLLBACK TO.

### Savepoint
Определив точку сохранения с помощью SAVEPOINT (вложенные транзакции), при необходимости можно вернуться к ней с помощью команды ROLLBACK TO, а не начинать всю транзакцию заново.

### Транзакционные DDL особенности
В Postgres можно менять структуру таблицы и это не приведет к неявной фиксации транзакции. То есть внутри транзакции можно например выполнить alter table и в случае необходимости откатить.

**Уровни изолирования**  
В стандарте SQL описывается четыре уровня изоляции транзакций:
- Read uncommited (Чтение незафиксированных данных) - в Postgres работает как Read committed.
- Read Committed - видит только те данные, которые были зафиксированы до начала запроса. Каждый оператор видит данные на момент своего начала работы.
- Repeatable Read - запрос в транзакции данного уровня видит снимок данных на момент начала первого оператора в транзакции.
- Serializable - полная изоляция. Используются блокировки так, чтобы пересекающиеся транзакции работали последовательно и не мешали друг другу. Во многих СУБД, в частности в PostgreSQL, сериализуемые транзакции сериализуются только с другими сериализуемыми транзакциями. Если в приложении много транзакций со слабыми уровнями изоляции, а вы добавляете новую транзакцию, для которой требуется сериализация, вам придётся пересмотреть все существующие транзакции, чтобы найти те, где необходимо «повысить» уровень изоляции. 

**Аномалии**  
**Dirty Read (грязное чтение)** - транзакция читает данные, записанные параллельной не зафиксированной транзакцией.

**Nonrepeatable read (неповторяющееся чтение)** – при повторной выборке одной и той же записи данные в ней изменились.

**Phantom Read (фантомное чтение)** – при повторной выборке данных внутри одной транзакции пришел разный набор строк.

**Serialization anomaly (аномалия сериализации)** — при разной последовательности выполнения транзакций получается разный результат.

**Lost update (потеря обновления)** – две транзакции читают одни и те же данные для обновления но одна из транзакций затирает обновления другой.

**Блокировки на уровне строк**  
Блокировки на уровне строк блокируют только запись в определённые строки, но никак не влияют на выборку. Снимаются такие блокировки в конце транзакции или при откате к точке сохранения. Бывают эксклюзивные и разделяемые.

**Эксклюзивные блокировки:**  
FOR UPDATE - выданные оператором SELECT, блокируются как для изменения. Это плохо сказывается на производительности – операции чтения в других транзакциях сразу же встают в очередь, ожидая завершения всей транзакции. Не блокирует обычный SELECT без использования FOR UPDATE/SHARE.
SKIP LOCKED - пропустить заблокированные строки. Позволяет выбрать что именно блокировать тогда как serializable-транзакция блокирует все.
FOR NO KEY UPDATE - действует подобно FOR UPDATE, но запрашиваемая в этом режиме блокировка слабее: она не будет блокировать команды SELECT FOR KEY SHARE, пытающиеся получить блокировку тех же строк.

**Разделяемые блокировки:**  
FOR SHARE - действует подобно FOR NO KEY UPDATE, за исключением того, что для каждой из полученных строк запрашивается разделяемая, а не исключительная блокировка. Разделяемая блокировка не позволяет другим транзакциям выполнять с этими строками UPDATE, DELETE, SELECT FOR UPDATE или SELECT FOR NO KEY UPDATE, но допускает SELECT FOR SHARE и SELECT FOR KEY SHARE.

FOR KEY SHARE - действует подобно FOR SHARE, но устанавливает более слабую блокировку: блокируется SELECT FOR UPDATE, но не SELECT FOR NO KEY UPDATE. Блокировка разделяемого ключа не позволяет другим транзакциям выполнять команды DELETE и UPDATE, только если они меняют значение ключа (но не другие UPDATE), и при этом допускает выполнение команд SELECT FOR NO KEY UPDATE, SELECT FOR SHARE и SELECT FOR KEY SHARE.

**Конкурентность и блокировки**  
В некоторых случаях можно избежать ошибок конкурентности с помощью ограничений БД, например — уникальных ключей или ограничений по значению (например не может быть меньше нуля).

Если отсутствует объект на который можно наложить блокировку то его можно создать искусственно, чтобы использовать оператор select for update – такой подход называется материализация конфликтов.

**Двухфазная блокировка 2PL**  
В отличии от блокировок снимков данных, при 2PL записывающие транзакции блокируют не только другие записывающие но и читающие. Такая блокировка защищает от всех аномалий. Такой подход используется для уровня изоляции serializable. При таком подходе возможны взаимные блокировки, БД их сама распознает и прерывает одну из транзакций.
Такой подход значительно снижает производительность, так как одни транзакции ждут другие. Одна длительная транзакция может заблокировать много других запросов на чтение.

**Предикатная блокировка (predicate lock)**  
Это тип блокировки, который предотвращает изменение всех строк данных, удовлетворяющих определенному условию.

## Индексы
Индекс - отсортированный набор значений, связанных с таблицей или представлением с конкретной колонкой, который ускоряет получение данных. С помощью индексов можно как повысить так и понизить производительность (они замедляют CUD). Индексы используют для полей по которым ведется поиск.

Индексы используются для поиска по колонкам таблицы, для ускорения сортировки, для проверки ограничений (например unique).

Плюсы чтения из индекса, а не из таблицы:
- Индексная таблица весит много меньше таблицы с данными, а значит элементарно может быть прочитана быстрее.
- СУБД чаще всего стараются кешировать индексы в оперативную память, которая сама по себе много шустрее жёсткого диска*.
- В индексах отсутствуют дублирующиеся строки. А значит, как только мы нашли первое значение, поиск можно прекращать - оно же и последнее.
- Данные в индексе отсортированы. Это позволяет использовать алгоритм бинарного поиска (он же метод деления пополам), эффективность которого многократно превосходит простой перебор.

## Какие индексы бывают в Postgres
**B-tree** - тип индекса по умолчанию. Представляет из себя сбалансированное дерево. Т.е по разные стороны от промежуточного узла расположено примерно одинаковое колличество узлов. Эффективны для поиска по условию равенства, принадлежности диапазону, совпадения с null, сравнения больше\меньше. Для индексирования подходят любые типы данных. Кроме того, индекс на основе B-дерева ускоряет сортировку результатов, если в ORDER BY указано проиндексированное поле.

**Hash** - индексы на основе хеш-таблиц. Применяются когда нужен поиск по условию равенства.

**GIN** - Применяется когда несколько значений нужно отобразить в одну строку. Применяется для структур данных, таких как массивы и для полнотекстового поиска.

**GIST** - Полезен для индексации геометрических типов данных и для полнотекстового поиска.

**BRIN** - для больших таблиц. Он медленнее B-tree но занимает меньше места.

## Категории индексов
**Частичный** - индексируется только подмножество таблицы (в индексе фигурирует Where). Это позволяет сделать индекс более быстрым и легковесным.

**Уникальный** - гарантирует, что каждое значение встречается только один раз.

**По нескольким столбцам** - для ускорения запросов с условием по нескольким столбцам.
**По выражению** - можно строить по выражениям и даже функциям.

## Покрывающий индекс
Это индекс, которого вполне достаточно для ответа на запрос без обращения к самой таблице.

## Составной индекс
Это индекс созданный по нескольким столбцам таблицы (до 32 столбцов). Поддерживается типами индексов: B-дерево, GiST, GIN и BRIN.
Такие индексы имеет смысл использовать, когда в одном запросе фигурируют более одной колонки.
Первой должна идти колонка, по которой фильтруем.  
Составной индекс может использоваться также и для одного поля если оно входит в индекс.

## Explain
Команда explain показывает каким образом будет выполняться запрос чтения данных. При наличии опции analyze команда выполняет и возвращает фактическое время выполнения и колличество строк.

Избирательность индекса - планировщик решает применять индекс или нет в соответствии со стоимостью плана выполнения.
С помощью этой команды можно узнать пошаговый план выполнения запроса на чтение.

- Seq Scan - последовательное, блок за блоком, чтение данных таблицы.
- Index Scan, Index Cond - используется индекс.
- Filter - значит каждую строку сравнивают с условием.
- cost - это не время, а некое сферическое в вакууме понятие, призванное оценить затратность операции. Первое значение - затраты на получение первой строки. Второе - затраты на получение всех строк.
- rows - приблизительное количество возвращаемых строк при выполнении операции Seq Scan.
- width - средний размер одной строки в байтах.

Команда EXPLAIN кеширует результаты, для сброса кеша нужно запустить ANALYZE tbl_n;  
EXPLAIN (ANALYZE) query; - чтобы получить реальное время выполнения.  
EXPLAIN (ANALYZE, BUFFERS) - BUFFERS показывает сколько операций ввода\вывод было сделано.

- Составной тип - представляет структуру табличной строки или записи; по сути это просто список имён полей и соответствующих типов данных.

## Чем JSON отличается от JSONB?
JSONB - двоичная разновидность формата JSON, у которой пробелы удаляются, сортировка объектов не сохраняется, вместо этого они хранятся наиболее оптимальным образом, и сохраняется только последнее значение для ключей-дубликатов. JSONB обычно является предпочтительным форматом, поскольку требует меньше места для объектов, может быть проиндексирован и обрабатывается быстрее, так как не требует повторного синтаксического анализа.

## Функции и процедуры
С помощью языков SQL, pgSQL, Python, C и других можно создать свою функцию или процедуру и повторно ее использовать.

| Функции | Хранимые процедуры |
|---|---|
| Функция имеет возвращаемый тип и возвращает значение | Хранимая процедура не имеет возвращаемого типа, но имеет выходные аргументы |
| Использование DML (`insert`, `update`, `delete`) запросов внутри функции невозможно. В функциях разрешены только `SELECT`-запросы | Использование DML-запросов (`insert`, `update`, `delete`) возможно в хранимой процедуре |
| Функция не имеет выходных аргументов | Хранимая процедура имеет и входные, и выходные аргументы |
| Вызов хранимой процедуры из функции невозможен | Использование или же управление транзакциями возможно в хранимой процедуре |
| Вызов функции внутри `SELECT` запросов возможен | Вызов хранимой процедуры из `SELECT` запросов невозможен |

Функции могут быть изменяемые, не изменяемые и стабильные, не изменяемые возвращают один и тот же результат при тех же аргументах - этохорошо для производительности. Функцию можно пометить как не изменяемую.

## Триггеры
Триггер позволяет вызывать процедуру, если над таблицей или представлением выполняется команда INSERT, UPDATE, DELETE, TRUNCATE. Вызываемая триггером процедура может модифицировать изменившиеся данные или просто выполнить необходимую операцию.

Триггеру можно задать момент срабатывания: BEFORE, AFTER, INSTEAD OF. Если определено несколько триггеров для одной таблицы то они запускаются в алфавитном порядке.

Чтобы не выносить бизнес логику в триггер нужно определить: если бы данные были нормализованы, то была бы нужна такая функция? Если ответ положительный - это бизнес логика. Отрицательный - обеспечение целостности данных, а значит триггеры уместны.

С помощью триггеров можно:
- вычислять значения вместо агрегации при каждом запросе.
- валидировать данные и выдавать ошибку если валидация не прошла.

Минусы триггеров:
- они могут замедлять запросы.
- бизнес логику лучше держать на уровне приложения.

## Представления (Views)
Представления можно считать именнованным запросом или оберткой над select. Каждый раз когда вызывается представление оно выполняет заложенный в него запрос. Представление может быть обновляемым но для этого должен выполняться большой список условий. Представление может быть временным. Представление может быть материализованным (хранится физически).
Могут служить для инкапсуляции реального устройства таблицы.
Для легкого повторного использования запроса без его ввода целиком.
Для повышения производительности путем кеширования результатов.
Для предоставления доступа только к части записей таблицы.

## CTE
Общие табличные выражения - позволяют один раз создать подзапрос и присвоить ему имя, а затем использовать его в нескольких местах главного запроса.

В CTE можно использовать не только select но и insert, update, delete.

В одном WITH может быть несколько CTE.

Одно CTE может ссылаться на другое CTE (определенное раньше).

CTE исполняется только один раз а потом результат берется из кеша.

CTE с оперератором select выполняется только в том случае если его вызывают в основном запросе, но CTE изменяющие даныне выполняются всегда.

С помощью CTE можно ускорить выполнение подзапроса если он вызывается несколько раз. А так же сократить размер самого запроса.
